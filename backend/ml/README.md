# 병용금기 예측 모델 (DDI Link Prediction) — 학습 + 평가 리포트

## 배경

`drug_interactions` 테이블(324,321쌍, 중복 정리 후)은 실제로는 **132개의
성분/계열 단위 기전(mechanism) 규칙**이 약품 조합으로 전개된 결과다. 전체
35,299개 약품 중 DUR에 상호작용 기록이 하나라도 있는 약품은 8,227개
(약 23%)뿐이고, 나머지 약 77%(27,072개)는 "안전이 검증된 것"이 아니라
"DUR이 아직 다루지 않은 것"이다. 이 모델은 DUR에 없는 약품 쌍의 위험도를
계열·성분·그래프 구조로부터 추정한다.

## 방법

- **노드 특징**: `class_name`(치료 계열, 35,250/35,299 = 99.9% 커버), `ingr_name`의
  `dur_code`(성분 코드, 7,628/35,299 = 21.6% 커버)
- **그래프 임베딩**: train 엣지로만 만든 인접행렬에 TruncatedSVD(64차원) —
  설명분산 85.2%
- **쌍(pair) 특징**: same_class, class_pair_density(계열쌍 위험 밀도, train만),
  ingr_jaccard(성분 자카드 유사도), embedding dot/cosine/L2
- **모델**: HistGradientBoostingClassifier (scikit-learn)
- **음성 샘플링**: 무작위 전체 인구에서 뽑으면 고립 노드(임베딩=0벡터)가
  섞여 과제가 인위적으로 쉬워짐 → "이미 알려진 상호작용이 있는 약품"
  집합(8,227개) 안에서만 하드 네거티브를 샘플링

## 평가 결과 (`artifacts/eval_report.json`)

| 평가 방식 | AUROC | AUPRC | 의미 |
|---|---|---|---|
| **무작위 엣지 15% 분할** (hard negatives) | 0.9995 | 0.9995 | "이미 아는 계열 조합의 새 제품쌍" — 규칙이 대부분 train에도 남아있어 낙관적 |
| 무작위 엣지 15% 분할 (easy/전체인구 negatives) | 0.9997 | 0.9996 | 참고용, 가장 낙관적 |
| **계열쌍(class-pair) 자체를 15% 통째로 hold-out** | **0.4847** | 0.8226* | "DUR이 한 번도 다루지 않은 새 계열 조합" — 사실상 무작위 수준 |

\* AUPRC는 이 분할에서 양성:음성 비율이 불균형(35,895:7,523)해 절대값이
부풀려져 보임 — AUROC가 더 신뢰할 수 있는 지표.

## 결론 (정직하게)

이 모델은 **두 가지 서로 다른 과제에서 완전히 다른 성능**을 보인다.

1. **"이미 알려진 위험 계열의 새 제품 확장"** — 매우 정확함(AUROC 0.9995).
   예: A 계열과 B 계열이 이미 여러 제품쌍으로 병용금기 판정을 받았다면,
   같은 두 계열의 신규 제품 조합도 높은 신뢰도로 예측 가능.
2. **"DUR이 전혀 다루지 않은 새로운 계열 조합 발견"** — 사실상 무작위
   수준(AUROC 0.4847). `class_pair_density`가 permutation importance
   0.3388로 가장 큰 기여를 하는데, 이는 정의상 학습된 계열쌍에서만 값을
   가지므로 완전히 새로운 조합에는 아무 정보도 주지 못한다. 나머지
   특징(임베딩, 성분 자카드)만으로는 신호가 거의 없다.

**"가장 정확한 모델"이라는 표현은 과제 1에만 해당한다.** 과제 2(진짜 미지의
위험 발견)를 잘 풀려면 이 DB에 없는 데이터 — 화학 구조(SMILES),
약리기전 온톨로지, 임상 문헌 기반 특징 — 가 필요하다. 이는 향후 과제로
남겨둔다.

## DUR에 없는 쌍이 "안전"이라는 뜻은 아니다

음성 라벨은 무작위 샘플링 근사치이며, 실제 안전성 검증이 아니다. API/앱에
예측 결과를 노출하려면 "공식 병용금기(DUR)"와 "AI 추정 위험"을 명확히
구분하는 별도의 제품 결정이 필요하다 (이번 작업 범위에는 포함하지 않음).

## 재현 방법

`scikit-learn`/`scipy`/`numpy`/`joblib`은 연구용 `ml` poetry 그룹에만 있고
프로덕션 메인 의존성에는 없다 (서빙에서 빠졌으므로).

```cmd
cd backend
poetry install --with ml
poetry run python ml/train_ddi_model.py
```

## 산출물

- `artifacts/ddi_model.joblib` — 학습된 모델 + 노드 임베딩 + class_density prior
- `artifacts/eval_report.json` — 전체 평가 지표 (위 표의 원본)

## 왜 서빙에서 뺐는가 (2026-07-15)

한때 `app/services/ddi_ml_service.py`로 quick-check에 하이브리드 통합했으나
(규칙 1순위 + 규칙에 안 걸린 쌍만 확률 0.85 이상 시 "ml_estimated"로 보조 표시),
아래 실험으로 실질 가치가 없음을 확인하고 제거했다.

미커버 쌍 30만 개를 무작위 샘플링해 실제로 몇 개가 신뢰도 0.85를 넘는지,
그리고 SQL 한 줄로 계산 가능한 단순 규칙(`class_pair_density > 0`, "이 두
계열이 이미 DUR 병용금기 쌍을 하나라도 가지고 있다")과 비교했다.

| 지표 | 값 |
|---|---|
| 0.85 이상으로 플래그된 쌍 | 300,000개 중 194개 (0.065%) |
| 그 중 `class_pair_density > 0`(=단순 규칙으로도 잡히는 쌍) | **194개 (100%)** |
| ML만 찾아내고 단순 규칙은 못 찾은 쌍 | **0개** |
| 단순 규칙(`density > 0`)으로 플래그된 쌍 | 44,593개 |

즉 모델이 자신 있게 찍은 쌍은 전부 SQL 한 줄로 이미 알 수 있는 부분집합이었고,
심지어 그 SQL 규칙보다 훨씬 더 적게(0.4%만) 잡아냈다 — 모델이 추가 정보를
전혀 제공하지 못하고, scikit-learn 의존성·아티팩트 관리·재학습 필요성
(약품이 추가될 때마다 `node_index`가 stale해짐)이라는 복잡도만 늘렸다.
그래서 규칙 기반 3단계(critical/caution/safe)로 되돌리고, 이 실험은 연구
기록으로만 남긴다.
